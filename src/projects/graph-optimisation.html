01 / Context

The project.

A C# player-side routing implementation for a supplied graph runtime. The public implementation and whitepaper cover routing and storage; the runtime itself is not included.

02 / Problem

What needed solving.

The agent starts without a complete map. It must explore, remember routes and account for resources and locks while collecting objectives and reaching an exit. Repeated searches make memory representation a practical design concern.

03 / My contribution

My part in the work.

I built the player-side routing implementation: incremental discovery, BFS, weighted and lock-aware routing, resource handling, objective planning, custom heap/hash storage and action buffers. The supplied runtime and harness are separate from this public implementation.

04 / Architecture & implementation

How the pieces work.

Graph and traversal state use contiguous arrays. BFS handles reachability, Dijkstra handles weighted paths, and custom priority-queue/hash storage supports repeated lookup and routing. Search stamps avoid clearing complete state arrays for every search.

05 / Engineering trade-offs

Why these choices.

  1. Store traversal state contiguously

    Use flat arrays rather than an object-heavy graph to keep the storage and repeated traversal behaviour explicit.

  2. Choose search by the question

    Use BFS when reachability and unweighted distance are enough; use Dijkstra when edge costs affect route selection.

  3. Reuse search storage

    Use stamps and reusable buffers to avoid repeatedly resetting or allocating full search state.

06 / Evidence & verification

Results and verification.

The public repository contains the C# implementation and a technical whitepaper explaining the algorithms and complexity. The supplied runtime is absent, so this repository alone is not a standalone application and no fresh runtime benchmark is claimed.

  • BFS: O(V + E).
  • Dijkstra with a heap: O((V + E) log V).
  • Complexity analysis is not a measured speedup.

Public C# implementation and technical report; scope constrained by the absent supplied runtime.

07 / Limitations

Limits and next steps.

The harness is needed for a representative end-to-end run. With an available harness, I would compare against a simple baseline across fixed seeds and report correctness, allocations and runtime separately, including unsuccessful routes.
