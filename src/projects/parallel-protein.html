01 / Context

The project.

An individual coursework report on optimising a supplied C++ protein-signature program. The supplied algorithm, ISAAC, uthash and OpenMP are existing building blocks; my work focused on data layout, state ownership, output and measurement.

02 / Problem

What needed solving.

Adding threads does little if workers contend over mutable lookup state or serialize their output. The challenge was to expose independent work without changing the signature bytes produced by the supplied program.

03 / My contribution

My part in the work.

I redesigned record-level ownership, replaced hot-path mutable canonical lookup work with an immutable table, used bounded narrower accumulators, assigned disjoint output ranges and benchmarked the versions. This was performance engineering of supplied coursework software, not a new biological analysis algorithm.

04 / Architecture & implementation

How the pieces work.

Records are indexed before a static OpenMP parallel-for. Input and canonical tables are read-only; each iteration owns local accumulators and an exact output slice. Prefix offsets place results into one contiguous buffer, followed by a serial write after the barrier. The retained reader preserves the legacy EOF pass for compatibility.

05 / Engineering trade-offs

Why these choices.

  1. Give each record its own output

    Use local accumulators and disjoint prefix-defined slices instead of locks around each record. A final contiguous buffer preserves deterministic ordering, at the cost of retaining that buffer in memory.

  2. Precompute an immutable lookup table

    The fixed 20-symbol, 3-mer domain has 8,000 entries. Direct indexing removes mutable hash/RNG work from the hot path, trading setup/storage for simpler repeated computation.

  3. Prove a smaller accumulator safe

    At most 14 overlapping 3-mers contribute -1, 0 or +1 within a full partition, bounding each component to [-14,+14]. A 16-bit accumulator is sufficient and compiler-SIMD-friendly; no hand-written intrinsics are claimed.

06 / Evidence & verification

Results and verification.

Summary statistics were recomputed from all 60 retained qut3 timings during this refinement. The eight-thread mean was 0.1807455 seconds versus 0.5882820 seconds for the V6-derived optimised sequential baseline: 3.254753×, reported as 3.25×. Ten runs per configuration followed one warm-up, with forward/reverse ordering. Recorded comparison and hash checks match the reference output for every tested configuration. No executable was rebuilt or benchmark rerun for the portfolio.

07 / Limitations

Limits and next steps.

Internal application timing includes setup through output close but excludes process startup and durable-storage fsync. CPU affinity and frequency were not controlled. Serial read/layout/output limit scaling, and the reader’s correctness scope is narrow. Byte identity on the recorded inputs is not exhaustive correctness for malformed or arbitrary FASTA data. I would next benchmark memory use, scheduling choices and additional fixed workloads under a controlled runtime.
