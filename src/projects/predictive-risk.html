01 / Context

The project.

A desktop ML application built around a 30,000-record credit dataset. The project combines a PyQt6 interface, training utilities, service boundaries and MySQL-oriented history/reporting.

02 / Problem

What needed solving.

A trained classifier is only one part of an application. Inputs need a consistent schema, predictions need model context, and users need to review results and history without navigating training code.

03 / My contribution

My part in the work.

My focus was the application around the model: PyQt6 screens, services, domain objects, prediction flow, reporting and model-management concepts. This prototype does not represent a deployed lending service or bank-grade validation.

04 / Architecture & implementation

How the pieces work.

The UI calls a service layer rather than training code directly. The training workflow compares calibrated Logistic Regression, XGBoost and LightGBM. Structured prediction outputs carry probability, risk label and model context, while MySQL-oriented services support history and reporting.

05 / Engineering trade-offs

Why these choices.

  1. Separate interface and services

    Keep UI screens, application logic, ML utilities and domain objects separate. This adds explicit interfaces but makes model and presentation changes less coupled.

  2. Use an interpretable comparison baseline

    Compare boosted trees with calibrated Logistic Regression. Model selection needs reproducible held-out evidence rather than a preference for complexity.

  3. Store prediction context

    Track model identity alongside structured outputs and history. That improves traceability, while introducing versioning and data-governance responsibilities.

06 / Evidence & verification

Results and verification.

The public repository contains the PyQt6 application, training code and 30,000-row data files. The training implementation includes Logistic Regression, XGBoost and LightGBM. The file under tests/ launches the application; it is not an automated test suite.

  • Training code implements calibrated Logistic Regression, XGBoost and LightGBM.
  • The 30,000-row files were counted; dataset size is not a validation result.
  • No genuine saved evaluation arrays or screenshots were available; fallback demo plots are not used.

Public source and data-shape inspection at commit e4c11bc8. Model training, application execution and financial validation were not reproduced.

07 / Limitations

Limits and next steps.

No held-out model-quality result was independently reproduced. The dashboard can fall back to simulated metrics when saved evaluation arrays are absent, so those visuals are excluded here. Expanded-history feature provenance also needs documentation. Before any operational use, I would add service tests, leakage/calibration checks and a fairness/threshold review; this is not a validated lending service.
