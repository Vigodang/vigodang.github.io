Problem

A machine-learning model by itself is not an operational system. Users need ways to enter data, run predictions, review risk, compare models, inspect reports and manage application workflows.

What I Built

I built a desktop credit-risk application combining a PyQt6 UI, machine learning, a service layer, MySQL-oriented workflows, model management, reporting, data quality utilities and optional Gemini-assisted explanations.

How It Works

The training workflow implements XGBoost, LightGBM and calibrated Logistic Regression on a fixed model input schema. At runtime, the app returns a structured prediction result with probability, risk label and model identity/context.

My Contribution

My focus was turning the ML workflow into an application: UI screens, services, models/domain objects, prediction workflow, reporting and model-management concepts.

Key Technical Decisions

  • Separate UI, services, ML utilities, domain models and configuration.
  • Use a stratified train/validation/test split in the training workflow.
  • Represent prediction outputs as structured objects rather than loose values.
  • Include model registry and active-model concepts so prediction is not tied to one hard-coded model.

Evidence

The repository documents a 30,000-row base dataset, a 30,000-row training dataset and a class distribution of 23,364 non-default and 6,636 default records. The training workflow implements XGBoost, LightGBM and calibrated Logistic Regression.

I am not claiming automated test coverage for this repository because the discovered `tests/main.py` file is an application launcher, not a test suite.

What I Learned

I learned how different it feels to turn a model into software people can operate. The difficult parts were not only model training, but input structure, state, reporting, governance and public-safe release hygiene.
