01 / Context

The project.

An engineering project extending a social media backend with a multimodal assistant and asynchronous media processing. The public source spans the backend, ACP adapter and MCP tools.

React static app on GitHub Pages. Posts, comments and demo identities stay in memory in the current tab. Authentication, ACP/MCP activity and AI responses are simulated. This portfolio adaptation builds on existing starter code and upstream social interface work; the original engineering contribution is described separately below.

02 / Problem

What needed solving.

A conversational assistant needs useful access to personal media, but model-generated tool calls must not decide who the user is or which records they own. Slow classification and embedding jobs also need a separate lifecycle from the upload request.

03 / My contribution

My part in the work.

My work covered the agent and MCP tool boundary, user-isolated retrieval, asynchronous media processing and retry behaviour. The wider application includes a social media backend and client integration; this case study describes the agent and media-processing components I worked on.

04 / Architecture & implementation

How the pieces work.

ACP carries the conversational stream. MCP exposes read-only backend tools. A configured server-side demo identity scopes tool access and vector retrieval. Separately, S3 events flow through EventBridge and SQS into classification and embedding work, with state in DynamoDB and retrieval through S3 Vectors.

05 / Engineering trade-offs

Why these choices.

  1. Resolve identity in the server

    Server-scoped identity and ownership checks keep the model out of authorization decisions. The current demo uses a configured identity; a production identity lifecycle would add integration work.

  2. Separate conversation from capabilities

    ACP carries the stream while MCP exposes read-only tools. This makes each boundary testable, at the cost of coordinating contracts across separate services.

  3. Queue classification and indexing

    S3 events route through EventBridge and SQS so inference does not block uploads. The trade-off is an eventual result with retry, duplicate-delivery and job-state handling.

07 / Limitations

Limits and next steps.

The MCP service uses a configured demo identity; production multi-user authentication and authorization remain future work. Passing local tests does not demonstrate production operation, scale or a complete security review. I would next reproduce a deployed integration run with failure injection, queue backlog observation and explicit end-to-end latency measurements.
